# 结构版式与图解方法

## A. 三段流程：最常用

**适用**：一个机制如何把输入转成输出，或中间层如何改变双方关系。

- 横向排版 `起点 → 中间机制 → 结果`。
- 每段一个主体和一条明确的关系线。
- 角色、物件、连线优先；切勿在每个节点里堆 4 条解释。
- 范例：`用户 → 超级导购 → 店家`，若“交易权”改变，增加钱的流向并切断商家直接联系顾客的线。

## B. 三栏对比：同一事例、三个规则

**适用**：A2UI / Intelligent UI / 代码生成，三种技术路线或产品方案。

- 三栏使用同一视角、同一旅程或同一业务场景，让真正的规则差异凸显。
- 每栏最多一个主场景和一个可见状态机制，不要重复整套景点酒店餐厅。
- 范例：`固定行程` vs `预案条件分支` vs `自由生成但被沙箱圈住`。
- 共同条件采用相同象征物；差异通过路线分叉、围栏或修改权限来表示。

## C. 两栏机制：有形解释 vs 抽象推演

**适用**：物理引擎 vs 世界模型，传统机制 vs 新机制。

- 左栏具体因果：物体、作用力、接触结果、规律路径。
- 右栏整体环境：状态表示、未来分支、预测候选。
- 两栏视觉分量相等，不把右侧无缘由画成“更厉害”的超级大脑。

## D. 分层架构：中心协调、多单元并行

**适用**：读者需要理解交互入口、调度者和执行单元的分工，例如 Router–Worker 架构。若题目关注事件先后或单条请求的处理过程，选 A 的流程版式。

- **上方是交互**：把用户或事件入口放在核心角色上方，依据真实交互决定是否画请求与回复双向连接。
- **中央是调度**：用画面中最大的一块横向区域承载核心角色。把接单、派单和回传等职责压缩成一行；可以用有明确职责的角色造型增强辨识度。
- **下方是执行**：把并行单元放在同一基线上，用等大的对象表现同级。若工单与执行会话一一对应，工单跟随各自支路或并入工位。分叉发生在调度者侧。
- **辅助能力放侧边或底层**：用较小的组表示状态、队列或人工监督。只画确定存在的依赖，并把这些依赖与任务流区分开。
- **示例：Super-agent**。上方是一位提出任务、接收回复的用户；中央是“Router · 前厅调度”，可用接待员和服务铃表达协调职责；下方是并排的 Worker 工位，每个工位带自己的工单。把“排队、持久状态”放在调度区侧边，支撑层的线条弱于派单线。一个概念总览可以把结果汇报和外部回复分别写进 Worker、Router 的职责，省去多条重叠的反馈箭头。

遇到指定原型、版本或文章时，先核对源文档中的组件、作用范围与连接。布局可以简化，权限和一对多关系要保持准确。

## E. 坐标/权衡曲线

**适用**：能力 vs 效率、通用性 vs 延迟等典型取舍。

- 真实绘制横轴和纵轴，方向必须与说明匹配。
- 若说明是“更强但更慢”，右侧能力更强时纵向效率应更低（曲线总体下降）。
- 用 2–4 个代表对象锚定曲线，最多一个弱化的未来/理想指向；不把概念曲线误称真实测量数据。
- 无字模式可以用闪电、计时器、可覆盖任务数量等图形做含义提示；文字模式优先标轴而非堆说明段落。

## F. 简洁单场景

**适用**：一段话只有一个真正要表达的隐喻。

- 使用一个完整场景，不分三栏，不制造五张缩略卡片。
- 范例：“前厅负责派单，后厨各管一口灶” → 一个前台调度员 + 右侧 3–5 个独立灶台；视觉重心放在前台和并行关系。
- 当用户说“更简单”，先退回这个结构，再决定要不要额外分组。

## 图像生成前的一句话自测

“用户不读文字，只看元素摆放和箭头，是否能准确区分谁能决定、谁能执行、资源来自哪里、变化是否被允许？”

不能的话，先改结构再追求质感。
